# Boards and Iteration Views

Read when the team wants a board or iteration view rather than plain
issues and milestones.

1. Fetch the current Projects capabilities from
   <https://docs.github.com/en/issues> — fields, views, automation, and
   the issue-to-project linking model evolve; design against the fetched
   page, not memory.
2. A board is a standing commitment: agree who grooms it and on what
   rhythm before creating it. A board nobody grooms misleads more than
   no board.
3. Start from the smallest structure that answers the team's actual
   question ("what is in flight?", "what is next?") — one view, few
   fields, statuses that mirror how work really moves. Add fields only
   when someone will keep them current.
4. Keep issues the source of truth: the board arranges them, it never
   replaces them. Automation that syncs status is configured from the
   fetched docs, never assumed.
5. Record in the AGENTS.md deposit: the board's location, what each
   status means, and who grooms it.
